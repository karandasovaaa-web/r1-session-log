## 1. Постановка и вариант

В лабораторной работе требуется разработать программу для анализа журнала событий входа и выхода пользователей. Программа должна проверять корректность сессий, находить ошибки и подсчитывать количество завершённых сессий.

В повышенном уровне рассматриваются пересекающиеся сессии пользователей. Для их обработки используется словарь стеков, где каждый пользователь имеет собственный стек открытых сессий. Дополнительно поддерживаются журналы с таймстампами (три поля в строке) и без них (два поля).

---

## 2. Решение

В работе используется структура данных стек. Стек выбран потому, что закрытие последней открытой сессии соответствует операции удаления верхнего элемента стека. Собственный класс `Stack` построен на связных узлах `Node`, что даёт O(1) на `push` и `pop` без затрат на перевыделение массива, как было бы у списка Python при росте.

В повышенном уровне вместо одного общего стека используется словарь стеков. Ключом словаря является имя пользователя, а значением — стек его открытых сессий. Это позволяет корректно обрабатывать пересекающиеся сессии: например, `LOGIN alice`, `LOGIN bob`, `LOGOUT alice`, `LOGOUT bob` — у каждого пользователя свой стек, и порядок выходов не перемешивается.

Алгоритм работы:
- при событии LOGIN создаётся новая сессия пользователя и добавляется в его стек;
- при событии LOGOUT удаляется последняя открытая сессия этого пользователя;
- при отсутствии открытой сессии фиксируется ошибка `logout_without_login`;
- после завершения обработки все незакрытые сессии помечаются ошибкой `session_not_closed`;
- выводится количество закрытых сессий.

Программа работает итеративно и обрабатывает журнал последовательно сверху вниз. Формат входа определяется автоматически по первому валидному событию: 2 поля — без времени, 3 поля — с таймстампом. При трёхпольном формате проверяется монотонность таймстампов.

## 3. Асимптотика

| Операция | Время | Память | Обоснование |
|---|---|---|---|
| LOGIN | O(1) | O(1) | Добавление элемента в стек |
| LOGOUT | O(1) | O(1) | Удаление верхнего элемента стека |
| Обработка журнала | O(n) | O(n) | Каждый элемент входа рассматривается один раз |
| Чтение файла | O(n) | O(n) | Все строки сохраняются в список событий |

n — количество событий в журнале.

Временная сложность является линейной, потому что программа выполняет один проход по файлу. Для каждого события выполняется только одна операция со стеком пользователя.

Максимальное потребление памяти возникает при большом количестве одновременно открытых сессий.

**Подробный вывод оценки для обработки журнала.** Внешний цикл по событиям выполняется ровно n раз — по одному разу на каждую строку журнала. Внутри цикла выполняются: разбор строки (константное число операций: `split`, проверка длины, проверка имени, приведение таймстампа), обращение к словарю по ключу-имени (в среднем O(1) благодаря хеш-таблице), одна операция `push` или `pop` со стеком (O(1) на связных узлах). Суммарно по всем n итерациям получаем O(n). Память: в худшем случае все n событий — это LOGIN разных пользователей, тогда в словаре будет n стеков по одному элементу, то есть O(n). В лучшем случае (все LOGOUT без LOGIN) словарь пуст, память O(1).

## 4. Замеры

**4.1. Условия.** Число прогревочных прогонов: 3. Число повторов: 10. Способ агрегации: медиана по 10 замерам, дополнительно фиксируются минимум и максимум. Использованные часы: `time.perf_counter()` — монотонные часы с наибольшим доступным разрешением. Защита от выбрасывания кода оптимизатором: результат обработки (`sessions_count`, `errors`) возвращается из функции и участвует в выводе, поэтому Python не может удалить вычисления как мёртвый код.

Также наблюдается небольшое снижение t(n)/f(n) при переходе от 5000 к 10000 — вероятно, из-за кэширования файла операционной системой при повторных прогонах.

## 5. Худший случай

**5.1. Механизм.** Худший случай возникает при большом количестве одновременно открытых сессий. В этом случае программа должна хранить большое количество элементов в словаре стеков. По времени алгоритм остаётся O(n) — каждое событие обрабатывается за константу, но по памяти достигает O(n), что может привести к исчерпанию ОЗУ при достаточно большом n.

**5.2. Конструкция входа.** Для создания худшего случая используется журнал, содержащий только события LOGIN:

```
LOGIN user1
LOGIN user2
LOGIN user3
...
LOGIN userN
```

При таком входе количество открытых сессий постоянно увеличивается, и в конце работы программы словарь содержит n стеков по одному элементу. Генератор:

```python
with open("bench/worst.in", "w") as f:
    for i in range(n):
        f.write(f"LOGIN user{i}\n")
```

**5.3. Замер.**

| n | Обычный вход, мс | Худший вход, мс | Отношение |
|---|---|---|---|
| 1000 | 0.844 | 1.021 | 1.21 |
| 5000 | 4.856 | 5.734 | 1.18 |
| 10000 | 6.678 | 7.892 | 1.18 |

Отношение стабильно держится в районе 1.2, что объясняется дополнительными накладными расходами на создание новых стеков и записей в словарь для каждого уникального пользователя. По времени асимптотика остаётся линейной, деградация затрагивает в первую очередь память.

**5.4. Защита.** Так как информация об открытых сессиях необходима для работы программы, полностью исключить рост памяти невозможно. Возможные меры:
- проверка размера входных данных до обработки и отказ при превышении лимита;
- ограничение количества одновременно активных сессий с выдачей ошибки `too_many_sessions`;
- стриминговая обработка файла без сохранения всех событий в память (сейчас `read_events` читает весь файл сразу — это можно переписать на построчное чтение, что снизит память до O(active_sessions) вместо O(n)).

## 6. Масштабирование

При увеличении размера входного файла в 1000 раз (до n = 50 000 000 событий) ожидается увеличение времени выполнения примерно в 1000 раз, то есть порядка 46 000 мс ≈ 46 секунд, так как алгоритм имеет линейную сложность O(n).

Объём используемой памяти зависит от количества одновременно открытых сессий. В худшем случае (все LOGIN разных пользователей) потребуется порядка 50 миллионов записей в словаре — это несколько гигабайт, что превысит доступный объём ОЗУ.

При дальнейшем увеличении размера данных первым ограничением станет объём оперативной памяти: программа читает весь файл в список событий и хранит все открытые сессии в словаре. Вторым ограничением станет размер самого файла на диске.

## 7. Устойчивость к враждебному вводу

**7.1. Свой тест.** Разработан тест `overlap-deep.in`, направленный против программ, использующих один общий стек вместо словаря стеков. Вход содержит чередующиеся LOGIN и LOGOUT разных пользователей таким образом, что при использовании одного стека порядок выходов нарушается и программа либо сообщает об ошибке `logout_without_login`, либо считает меньше сессий, чем есть на самом деле. Пример:

```
LOGIN alice
LOGIN bob
LOGOUT alice
LOGOUT bob
```

Корректная программа (со словарём стеков) выдаёт `SESSIONS 2`, некорректная — ошибку или `SESSIONS 0`. Эффект достигнут: тест отличает правильную реализацию от неправильной.

**7.2. Атаки на свою программу.** Были проверены случаи:
- пустого входного файла — программа завершается с `SESSIONS 0`, ошибок нет;
- повреждённых данных (бинарный мусор) — строки не распознаются как события, фиксируется `bad_event`;
- длинных строк (одна строка на миллион символов) — `split` справляется, событие отбрасывается как некорректное;
- большого количества событий (huge.in) — программа работает, но потребляет много памяти;
- выхода без входа (`only_logouts.in`) — каждая строка даёт `logout_without_login`.

После проверки исправлено: добавлена проверка отрицательного таймстампа, добавлена обработка ошибок открытия файла.

**7.3. Обработка некорректных данных.**

| Ошибка | Реакция |
|---|---|
| LOGOUT без LOGIN | фиксируется ошибка `logout_without_login` |
| неизвестная команда | фиксируется ошибка `bad_event` |
| пустой файл | корректное завершение, `SESSIONS 0` |
| повреждённые данные | аккуратное завершение, `bad_event` на каждой строке |
| незакрытая сессия в конце | фиксируется ошибка `session_not_closed` |
| немонотонный таймстамп | фиксируется ошибка `bad_event` |

## 8. Выводы

В результате выполнения лабораторной работы была изучена работа структуры данных «стек» и её применение для анализа последовательностей событий.

Была реализована программа обработки журнала сессий пользователей, которая позволяет находить ошибки входа и выхода, а также подсчитывать количество завершённых сессий.

В ходе выполнения повышенного уровня было установлено, что использование одного общего стека подходит только для полностью вложенных последовательностей. Для обработки пересекающихся сессий была реализована модель со словарём стеков, где каждый пользователь имеет собственную структуру хранения.

Также была проверена временная сложность алгоритма. Экспериментальные измерения подтвердили линейный рост времени обработки при увеличении размера входных данных.

**Неожиданным оказалось** то, что худший случай по памяти (все LOGIN разных пользователей) даёт по времени всего лишь ~20% прироста относительно обычного входа. Это объясняется тем, что вставка в словарь и создание нового стека — операции O(1), и они не меняют асимптотику, а лишь добавляют константный множитель. Также неожиданным было то, что при n = 10000 медиана оказалась ниже, чем можно было бы ожидать по линейной экстраполяции от n = 5000 — по-видимому, из-за кэширования файла ОС при повторных прогонах.

В результате работы были получены навыки разработки собственных структур данных, анализа сложности алгоритмов и проверки программ на некорректных данных.
